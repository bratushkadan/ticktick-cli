# План расширения TickTick CLI для веб-API v2

Добавить чтение списков и получение задач по ID через сессионную cookie. Описать HTTP-контракты уже реализованных методов и зафиксировать, какие детали подтверждены кодом, тестами и наблюдениями за сервером.

Изменения CLI только аддитивные. Существующие команды Open API, `v2 search`, `v2 completed`, `v2 focus`, команды привычек и `v3 active` сохраняют маршруты, флаги, форматы вывода, авторизацию и работу с кэшем. Новые команды регистрируются только под `v2`.

## 1. Уточнить контракт двух веб-маршрутов

По коду веб-клиента и минимальным GET-запросам на тестовых данных определить хост, обязательные заголовки, форму успешного ответа и поведение при ошибках. Сохранить обезличенные фикстуры для Go-тестов и указать, какие варианты были проверены. Cookie и ответы с пользовательскими данными в репозиторий не добавлять.

| Маршрут | Что проверить перед реализацией |
|---|---|
| `GET /api/v2/projects` | Форму коллекции, поля ID, имени и состояния списка, наличие закрытых списков и специальных списков вроде Inbox, наличие параметров или пагинации. |
| `GET /api/v2/task/:ids` | Формат и экранирование `:ids` для одиночного и группового запроса, форму ответа, порядок записей, поведение для смеси найденных и отсутствующих ID и для запроса без совпадений. Подтвердить, можно ли получать задачи из разных списков одним запросом и как ведёт себя маршрут для завершённых задач. Зафиксировать подтверждённый предел пакета, если он есть. |

## 2. Добавить методы Go-клиента и команды CLI

| Команда | Предлагаемый метод Go | Поведение |
|---|---|---|
| `ticktick v2 task get <task-id> [<task-id> ...]` | `(*V2Client).TasksByIDs(ctx, ids)` | Получить одну или несколько задач по исходным ID через `/api/v2/task/:ids`. CLI принимает отдельные позиционные аргументы и формирует путь по подтверждённому контракту. Вызов без ID или с пустым ID завершается ошибкой до HTTP-запроса. |
| `ticktick v2 project list` | `(*V2Client).Projects(ctx)` | Получить доступные списки через `/api/v2/projects`. Показать имя и ID для выбора списка, состояние и тип выводить при наличии подтверждённых полей. Параметры фильтрации и пагинации добавлять только при подтверждённой поддержке сервером. |

- Переиспользовать `V2Client` и общий HTTP-транспорт с cookie, таймаутом и обработкой ошибок. Для каждой команды выбрать origin по проверенному маршруту. Сохранить разделение настроек сессионной cookie и токена Open API.
- Для `task get` использовать одну форму результата для одного и нескольких ID. Предлагаемый JSON содержит `tasks` и, если контракт позволяет уверенно определить отсутствующие записи, `missingIds`. Частичный ответ должен сохранять найденные задачи и явно показывать, какие ID отсутствуют. HTTP-ошибку всего запроса обрабатывать как ошибку запроса.
- Для новых команд дать читаемый текстовый вывод и стабильный `--json`. В карточке задачи показать заголовок и метаданные, нужные для идентификации и проверки срока или статуса. Состав полей закрепить после проверки фикстур. Для обоих новых вызовов предлагается флаг `--original-ids`, чтобы получить ID для скриптов и существующих фильтров. По умолчанию использовать обезличенные ID, как в текущих командах веб-API. Добавить примеры работы с исходными ID из `v3 active --json --cache-ids`, `v2 completed --json --cache-ids` и `v2 project list --original-ids`.
- Новые команды выполняют прямые запросы на чтение. Они не требуют доступного каталога кэша и не обновляют снимки. Проверить отсутствие неявного перехода на Open API при ошибке cookie или отсутствии задачи.

## 3. Дополнить документацию веб-API

Сохранить в README таблицу команд и примеры. Добавить отдельный `docs/web-api.md` со ссылкой из README. Для каждого маршрута привести HTTP-метод, хост, путь, параметры, единицы и формат дат, правила передачи пустых значений и пример запроса с условными ID. Связать маршруты с экспортируемыми методами Go и командами CLI. Обновить справку `--help` новых команд и подсказки в `skills/ticktick/SKILL.md` для выбора команды по источнику ID и типу авторизации.

| Семейство | Что зафиксировать |
|---|---|
| `GET /api/v2/search/all` | URL-кодирование `keywords` и отсутствие запроса для пустого текста. `dueFrom` и `dueTo` независимо ограничивают **срок задачи** и передаются в Unix-миллисекундах. Показать `status=1&status=2` для завершённых, `status=0` для открытых, `projectId=ID1&projectId=ID2` и `tags=tag1&tags=tag2`. `includeClosed=true` передаётся по флагу. На уровне Go статусы задаются явно в `V2SearchOptions.Status`. |
| `GET /api/v2/project/{…}/completed…/` | Выписать три точных пути и их соответствие обычному `v2 completed`, `--all` и `--project`. Общая форма query `from=&to=…&limit=…`, даты в UTC `YYYY-MM-DD HH:mm:ss`, диапазон по **времени завершения**. Показать ручной переход через `nextTo`, повтор граничной записи и проверку продвижения курсора. Зафиксировать 100 как значение CLI по умолчанию и 1200 как наблюдавшийся размер страницы. Серверную разницу двух глобальных маршрутов отметить как открытый вопрос до сравнительной проверки. |
| `GET /api/v3/batch/check/{checkPoint}` | Целочисленный checkpoint в пути, `0` для полной синхронизации, `CheckPoint` из ответа для следующего вызова Go. Query и тела нет. `v3 active` выполняет полный запрос. Историю завершений и колонки веб-клиент запрашивает отдельно. |
| `GET /api/v2/pomodoros/statistics/…` | Полные пути `heatmap`, `dist`, `dist/clock`, `dist/clockByDay` и `generalForDesktop`. Описать назначение и поля ответа каждого. Для диапазонов в пути `YYYYMMDD`, `generalForDesktop` вызывается без параметров. Документировать единицы длительности по подтверждённым данным. |
| `POST /api/v2/habitCheckins/query` | Примеры JSON с одним `habitIds` и с числовым `afterStamp` в формате `YYYYMMDD`. Отметить, что в живой проверке из README возвращались записи строго после границы. При возможности повторить проверку на привычке с отметками до, на и после границы. Отличить отметки выполнения от записей дневника `/api/v2/getHabitRecords`. |
| `/api/v2/projects` и `/api/v2/task/:ids` | Добавить проверенные контракты, указать форму результата и обработку отсутствующих ID, показать `v2 project list`, одиночный и пакетный `v2 task get`. Указать соответствующие команды Open API и их маршруты. |

## 4. Проверить реализацию

- В тестах Go-клиента проверить на обезличенных фикстурах HTTPS-origin, HTTP-метод, точный путь и экранирование, сессионную авторизацию и декодирование. Покрыть одиночный и пакетный запрос, пустую коллекцию, частичный результат по подтверждённому контракту, `401`/`403` и некорректный JSON.
- В CLI-тестах проверить регистрацию обеих команд, вывод текста и JSON, флаг `--original-ids`, отсутствие запросов для некорректных аргументов и независимость от кэша. На примерах JSON проверить, что в вывод не попадают cookie и необъявленные поля ответа.
- Сохранить проверки HTTP-формы существующих запросов. В них уже покрыты повторяемые фильтры поиска, независимые границы, пропуск пустого запроса, три маршрута истории и `nextTo`, checkpoint, варианты Pomodoro и тело запроса отметок привычек. Прогнать `go test ./...` и проверить справку новых команд.
- После локальных тестов выполнить по одному проверочному вызову новых маршрутов с реальной cookie при наличии тестовых данных. Документировать подтверждённое поведение и открытые вопросы отдельно. Автоматические тесты должны проходить без cookie и внешней сети.

Порядок работ — подтвердить контракты, добавить методы и команды, сверить поведение с фикстурами и завершить документацию. Инкрементальная синхронизация в CLI и автоматическая пагинация истории остаются отдельными задачами, если появится сценарий, для которого недостаточно `BatchCheck` или ручного `nextTo`.
